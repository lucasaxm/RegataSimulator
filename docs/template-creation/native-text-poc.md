# Native text experiment: running and interpreting it

## Scope

`spikes/native-text/` is an **opt-in local native experiment**, separate from the unchanged Konva/Moveable browser spike. It does not start Spring/Telegram, load application configuration, read user images or change templates/schema/production rendering. It compiles standalone `NativeTextPoc`, `VisualCorrectnessPoc`, the shared `MagickCaptionFitter` and its pure test class, plus the existing plain `ProcessRunner`, outside Gradle/JAR source sets. Python uses the standard library; no package, global font or JDK installation is needed.

Generated literal/metacharacter, font, mixed, shared-slot text-only and literal K=0 fixtures and a local visual gallery have run as part of the [native feasibility work](backend-architecture.md#4-rendering-proof-of-concept-before-backend-implementation). **Magick is selected for authoritative backend text plus existing composition, and feasibility is accepted for development. By user agreement, stop PoC/gallery rounds and proceed with the backend.** Normal pt-BR glyph/alignment/layout issues become implementation regression tests, not phase-1 research blockers; no full comparison, Unicode audit or mandatory preview parity is required. Java2D remains retained comparison evidence, not an active production strategy. A small isolated Linux render smoke under actual sandboxing and unchanged caps is still required before production enablement; acceptance for development is not production readiness.

Creator HMAC/session bootstrap and the pure version-1 image/text definition/codec/validator are now implemented separately in production source, with synthetic tests; see [maintenance](../maintenance.md#creator-foundations-implemented-remaining-contracts-planned) and [typed definitions](text-areas.md#implemented-version-1-definition-foundation). Next comes durable SQLite submission/schema and versioned offline JSON bundle recovery, then renderer/workflow integration using those types. Production migration to SQLite is complete; JsonDB is maintenance-only for legacy compatibility/security fixes and existing stored-data import/export/recovery, not new creator definitions/origin/receipts/idempotency/migrations/workflow. Offline JSON is not the JsonDB engine or a fallback for new mixed data/receipts. Runtime/default retirement remains separate later scope; future unsupported creator persistence must fail closed clearly, not a behavior implemented here. Capabilities/submit/receipt endpoints, persisted mixed templates and production text/publication remain unimplemented; no real initData/Telegram end-to-end proof is claimed.

Initial optional [Preview is client-only Konva](backend-architecture.md#5-client-only-preview-and-deferred-alternatives), optionally using client-generated synthetic examples with no uploaded files or native-preview call; literal K=0 has no samples. Submit uploads only original + definition, never samples/previewId. Approximate browser output is acceptable without mandatory parity. `POST /api/creator/template-previews` is deferred, not a phase-2/3 implementation/test gate. No Node/Skia/headless-browser/Java2D migration is planned now; visible mismatch or failed correctness/resource gates can justify revisiting native preview, layer bitmaps or engines.

## Reproduce without application startup

The commands below are retained reference instructions, **not the next task or a request for more comparison/gallery rounds**. Do not rerun the PoC as a prerequisite for backend development. Preserve existing evidence; use implementation regression tests for remaining normal glyph/style behavior and a small sandboxed Linux smoke before production enablement.

Requires Python **3.12+**, an explicit **Java 21 JDK**, and an existing ImageMagick **7** native executable. Java 21.0.7 can run the local experiment but is not the maintenance-floor release JDK. macOS and POSIX/Linux process groups are supported; Windows is not tested/supported by this launcher.

Create a new owner-only parent under the **resolved** system temporary directory. Pass new child output paths: existing paths, symlink ancestry, shared output parents, repository paths and overlap with fonts are rejected. The launcher never sources `.env`/Spring profiles or trusts inherited Java/Magick configuration variables.

```sh
WORK=$(python3 -c 'from pathlib import Path; import tempfile; print(tempfile.mkdtemp(prefix="regata-native-text-", dir=Path(tempfile.gettempdir()).resolve()))')
python3 spikes/native-text/runner.py prepare-fonts --output "$WORK/fonts"
python3 spikes/native-text/runner.py self-test --java-home /absolute/path/to/jdk21 --fonts "$WORK/fonts"
python3 spikes/native-text/runner.py run --java-home /absolute/path/to/jdk21 --fonts "$WORK/fonts" --magick /absolute/path/to/magick --output "$WORK/smoke" --profile smoke --rounds 2 --sample-rss
python3 spikes/native-text/runner.py run --java-home /absolute/path/to/jdk21 --fonts "$WORK/fonts" --magick /absolute/path/to/magick --output "$WORK/boundary" --profile boundary --rounds 1 --sample-rss
```

Commands are run from repository root; paths are operator-selected **local tools**, never production credentials. Use a new result path for every rerun; retain failed results for comparison. Rendering reports/images start in private temporary storage, not tracked `build/`, user media or template directories. The visual gallery exporter below creates a persistent private copy outside the repository. Delete only owned experiment storage when evidence is no longer needed; exported galleries have no automatic deletion.

`prepare-fonts` is the only network operation: bounded download of the official Liberation **2.1.5** TTF archive into private storage, pinned archive/individual face/LICENSE SHA-256 values, bounded extraction rejecting links/unsafe headers and unmodified OFL notice retention. These digests identify reviewed downloaded artifacts; they are not an independent upstream signature/legal-clearance claim. Rendering is offline with those explicit font paths. Sans/Serif/Mono regular/bold are used; no font fallback/upload/URL support.

Pure launcher regression tests (no native process, download or real font dependency):

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s spikes/native-text -p 'test_*.py' -v
```

`self-test` compiles the complete standalone source list and runs injected-command fitter tests plus actual font/model/layout checks, but no ImageMagick execution. Fitter tests cover disjoint/non-monotone fit predicates, exact descending selection, fixed-size/floor/impossible cases, strict native-output parsing, rerender mismatch, scalar exhaustion, interruption/process-error propagation and unchanged NFD input bytes/owned paths. Ordinary Gradle tests remain independent of native tooling. IDE non-project import warnings do not imply `javac` failure; do not add these files to production packaging merely to satisfy the editor.

## What the profiles test

| Case | Proof / limitation |
| --- | --- |
| Owned UTF-8 file-fed `-annotate` / `caption:` | Decoded pixels for percent-expression, literal backslash versus newline, and leading `@` sentinel text. Compare an escaped literal oracle. No host secret files are used; this is a finite metacharacter matrix, not a full sandbox audit. |
| Fonts/layout | Six pinned faces, pt-BR accents, combining marks, multiple lines, long text, oversized words, outline, box fill and shrinking. Java uses grapheme-safe breaking and bounded positive size search. Unsupported glyphs, invalid surrogates/controls, excessive strings/boxes and impossible geometry fail explicitly in pure tests. |
| Native fitting | Shared explicit descending integer probes with `caption:split=true`, small sequential batches and strict free-height dimensions; the selected size is rendered again and its dimensions verified. Native auto-fit suggestions are no longer used. Fixed-height output alone is not evidence against clipping; internal grapheme/glyph coverage and line-height still need characterization. |
| Full small scenes | Generated template alpha, skew/off-canvas image distortion and masks, shared image/description slot, both text planes, text-only shared slot and all-literal `K=0`. Prototype empty-source resolution is tested; real repository/history/publication services are not invoked. |
| Image-only parity | Exact decoded pixels against the current native full-canvas source → template composition fixture. Independent Java ordering/placement checks compare exact opaque/transparent pixels; **fractional-alpha cross-engine quantization is excluded**, not passed off as pixel-identical output. |
| Boundary profile | 128 sequential small boxes per candidate; native-only 40MP canvas + small text attempt, without a full 40MP JVM decode. Cache/time failures are reported as capacity outcomes, not silently counted as completed renders. |
| Visual profile | Identical single-line phrase across six physical faces; left/center/right × top/middle/bottom alignment; red/green/blue/black/white fills; outline 0/1/3px; padding 0/8/20px; explicit blank/trailing paragraphs; combining marks, long shrink and oversized words. Invalid text/glyphs and impossible boxes require the expected typed rejection. See the proof boundaries below. |

The historical comparison profiles retain **Magick caption from a server-owned text file** and **Java2D/TextLayout box raster → existing Magick compositor**. Magick is now the user-selected backend direction; neither prototype implements the entire proposed text DTO/renderer contract. The full style catalogue, all outline bearings, complete adversarial/native limits and production integration still need their owning tests; browser metric parity is not mandatory. A successful profile or faster measurement does not establish correctness or readiness.

### Implemented bounded fitting, not production integration

Both native harness callers now share `MagickCaptionFitter`. It leaves the server-owned UTF-8 text bytes unchanged, enables `caption:split=true`, uses `-stroke none` when outline is disabled and does not use Java2D fitting to admit native captions. Native font/glyph and style admission still apply; Java2D remains a separate retained comparison.

1. Probe each integer from requested size (at most 128) downward, or only that exact size for controlled fixed-size cases. No binary-search/monotonicity assumption and no dependence on `caption:pointsize` suggestions.
2. Measure at most eight free-height captions per command. A 1×1 dummy image keeps the outer image list valid; each parenthesized probe emits its size/width/height and removes its image from the list with `+delete`. This avoids retaining a stack of every probe image, not a proven RSS bound.
3. Strictly require the expected number/order of responses, positive integer dimensions and the requested width. Missing, duplicate, reordered, truncated, diagnostic-contaminated or malformed output fails closed. Existing process failures/interruption propagate; they do not become a smaller-font fallback.
4. Select the highest fitting measured integer; every larger integer must have been measured and rejected. Render it explicitly again and require identical dimensions within the target content box. Unfitting probe images are never fully decoded into JVM heap. Free-height/dimension checks still do **not** prove caption-internal full glyph/grapheme coverage.
5. Per fit, enforce at most **128 probes**, **17 fitting commands including the final rerender**, and **16,000,000 scalar work units**, calculated as UTF-16 input length × size² for every probe and the final rerender. Stop with typed `FIT_WORK_LIMIT` before unaffordable work; do not skip untested larger sizes, silently normalize/truncate, increase timeouts or continue indefinitely. These counters exclude outer composition and separately reported diagnostic probes. Existing per-command/resource and whole-job deadlines remain.

The scalar budget is conservative experimental admission, **not a memory, CPU-time or production acceptance guarantee**. Larger exhaustive sweeps proved too expensive under the existing deadlines; metadata-only caption probing did not demonstrate a cheaper layout path. The deliberately heavy 96px long-text visual fixture now rejects explicitly with `FIT_WORK_LIMIT`, even though a smaller font can physically fit. Keep that rejected fixture visible as unfinished workload/capacity acceptance, not a rendering pass or a reason to raise caps. Ordinary smoke captions and the local 128-area boundary still execute under unchanged limits; neither establishes Spring/VPS headroom.

## Visual correctness and retained review

Run `runner.py run` with the same explicit tool/font options, a fresh output child, **`--profile visual --rounds 1`**. It renders a separate style matrix instead of running the timed smoke/boundary scenes. A failed rendering assertion gives a nonzero exit **after** writing `visual-manifest.json`, `visual-checks.csv` and available PNGs. Export those artifacts even when the candidate failed; do not chain export behind a success-only shell condition.

Create an owned **0700** persistent parent outside the repository, then invoke `gallery.py` with `--input /absolute/private/visual-output --output /absolute/private/persistent-parent/new-review`. The output must not exist and must not overlap the input or repository. Open the printed `index.html` directly in a browser: no server, CDN, package installation or public tunnel is needed. The gallery retains clean PNGs, guide PNGs, uncropped native annotation references, expected text/style/fitted size, each PASS/FAIL/LIMITATION, generated metadata and SHA-256 copy identities in `review.json`. Symlinks/traversal/nonregular files/overwrites are rejected; copied PNGs are signature/size checked, not independently decoded by the exporter. Budgets are 20MiB per PNG, 128MiB total and 200 files.

- **Bounds:** Java paints without a content/box clip into a 160px transparent guard. Every alpha pixel is scanned against box and padded content before producing the cropped clean image. Guides show orange box/cyan content/checkerboard outside; use them to inspect overflow, not just the final cropped image.
- **Font:** pinned file digests and physical names, no fallback for missing glyphs, plus distinct translation-normalized raster fingerprints for the identical 48px sample in all six faces. This establishes the tested face distinctions, not every Unicode glyph or browser metric equivalence.
- **Color/style:** exact fully covered fill/outline pixels, outline chroma including antialiasing, background corner and original-pixel dimensions. A thin centered 1px outline may have only subpixel coverage after fill; that opaque-outline check remains LIMITATION, not an invented pass. Lack of an exact opaque fill pixel in a small fitted native sample fails this strict gate but alone does not prove that the requested color was ignored.
- **Alignment/content:** Java compares actual painted bounds with physical glyph/stroke targets (2px raster tolerance), reconstructs wrapped text/explicit paragraphs exactly and verifies automatic shrinking. Native caption compares eligible single-line glyph pixels with a fresh uncropped annotation at the same face/size/colors/stroke. A mismatch may be internal clipping **or** different rasterization; it is not proof of clipping specifically. Native wrapping, combining-mark/full multiline coverage, requested line height and blank-line preservation remain LIMITATION: final outer overscan cannot detect internal caption clipping.

Historical local comparison passed the sampled Java painted-bound/alignment/font/color/content gates with the thin-outline caveat above. **Native caption failed alignment, some exact opaque-fill gates and single-line reference comparisons**; multiline/line-height/full-glyph proof is incomplete. Keep those failed outputs visible and transfer relevant normal-size cases to implementation regressions, resolving what each assertion establishes there rather than requiring more PoC/gallery rounds. They are not permanently desired failures, and acceptance for development does not turn them into passes. Both harnesses remain prototypes, not production runtime. The gallery's fit/1×/2× controls aid retained review; browser zoom/device scaling is not native-pixel proof.

### Comparison fairness and readability

The historical initial gallery mixed different fitting/styling policies. Its pass counts were not visual-quality approval or a measured engine ranking. The user subsequently preferred Magick visually and selected it, while the following caveats remain relevant:

- **Zero outline:** before correction, native commands supplied an outline color with `-strokewidth 0`, while Java skipped stroking. Native output still had an outline and the old check passed unconditionally. Native caption/literal paths in both harnesses now use `-stroke none` when disabled, with a contrasting-pixel absence regression in visual fixtures. This is not a production text implementation. An outline-color swatch alone does not mean the outline is enabled.
- **Thin outline:** Java paints a centered `BasicStroke` and then fills the glyph; the fill covers its inner half. Native painting produces a different visible thickness with the same numeric width. `controlled-outline-0/1/3` hold face, size (48px), text, fill, padding, alignment and box constant, varying only requested stroke width. These isolate the discrepancy; they do **not** establish normalized cross-engine outline semantics or claim that Java's faint stroke is visually satisfactory. A common visible-outline contract still needs implementation/proof.
- **Accent-sensitive native fitting:** before correction, NFD auto-fit suggested 7px even with split enabled, although explicit 28px measured 214×132 within 214×184. NFC suggested 31px whose free height exceeded the box and needed correction to 30px. The shared explicit fitter now selects **30px for both unchanged NFD and NFC fixtures**, checking all larger integers; source/owned-file hashes agree. `corrected-combining-fit` requires at least the independently measured 28px fit, replacing the old failing suggestion check. Original galleries retain that failure; fixed 28px control fixtures remain. This proves corrected dimension selection for these inputs, not identical Unicode rasterization or native full-glyph/grapheme preservation.
- **Oversized-word split:** the earlier isolated split option improved native auto-fit from 1px to 12px. `caption:split=true` is now integrated into shared probes/final renders and literal caption fixtures. Explicit descending measurement selects **13px** for the retained long-word fixture, with all larger integers rejected and final dimensions rechecked. `corrected-longword-fit` requires at least 12px. This is not a claim that native splitting is grapheme-safe for every Unicode input; full-glyph/layout gates remain.
- **Wrapping/line spacing:** Java applies its grapheme/paragraph layout and requested line-height multiplier. Native caption owns wrapping and does not apply that multiplier. Fixed-size comparisons remove font-size confounding, but do not establish identical wrapping, baseline, paint order or layout. Independent auto-fit samples must not be described as equal-size sharpness comparisons.
- **Magnification:** ordinary gallery zoom uses browser interpolation for both candidates; the pixel-inspection toggle explicitly switches to unsmoothed source-pixel enlargement. Neither creates new detail. At 1×/2× the viewport can scroll horizontally; a cut-off viewport is not evidence that the PNG clipped text. Inspect actual-size output and intended final display size as well.
- **Readability:** very long text in a tiny box is an adversarial capacity case, not the representative quality target. Preserving all text within bounds can legitimately produce unreadable small text. The gallery warns below an **illustrative 12 original-pixel fitted size** and never treats larger text as readability-approved. This is not a production font floor, a submission rejection or an agreed device/display threshold. The proposed finite **1px engineering fitting floor** is also not an agreed production readability cutoff. Initial optional Konva Preview is approximate, not a promise to reproduce eventual Magick fitting; revisit alternatives if visible mismatch emerges. This PoC adds no editor/API behavior.

Keep previous exported galleries unchanged for comparison. New visual manifests record fitting policy, measured sizes and rejected larger integers, actual fit counters/work, original/file text hashes, the independent 28px regression probe and readability caveats alongside failures. Input-byte preservation is not a native full-glyph proof. Visual judgment remains necessary even when sampled geometry/font/color checks pass. Magick is selected; Java2D remains historical comparison. Normal-size pt-BR output and consistent outline/layout semantics still need acceptance separately from stress cases.

## Bounds and evidence

- Java child uses headless mode and heap **64m/256m**; compilation is isolated and excluded from render measurements. Child environment is reduced to owned HOME/TMPDIR, local tool PATH and locale; inherited application secrets, Java options and user Magick configuration are not loaded.
- Native conversion/identify calls retain memory **128MiB**, map **256MiB**, disk **512MiB**, thread **2**, time **25 seconds**, with a **30-second** process runner. The standalone version query is separately time-bounded and does not accept conversion-limit prefixes.
- Each prototype job has a **90-second** deadline; the launcher bounds the overall child/compilation execution below **300 seconds**, kills owned process groups on interruption/timeout and retains bounded private Java diagnostics. Per-job native/text intermediates are cleaned, while generated fixture/result PNGs and reports are retained.
- Initial prototype text limits are 4,096 UTF-16 units, requested size ≤128 and box ≤2MP/2,048 per side. Smoke/boundary use a fixed inset; visual fixtures vary padding, line height, colors and outline within a bounded catalogue. Shared native fitting adds the probe/command/scalar budgets above; the separate Java comparison layout has an eight-million measured UTF-16 work-unit bound. The 90-second fixture/job and overall launcher deadlines remain unchanged. These are **experiment limits**, not production API guarantees; aggregate text/pixel/scratch/admission budgets still require Linux evidence.
- `checks.csv` records PASS/FAIL/**CAPACITY_REJECTED**. A zero exit or `external-metrics.json.succeeded=true` means the experiment child completed; **it does not turn rejected capacity cases into passes** or establish release readiness.
- For smoke/boundary, `measurements.csv` records case/engine wall time, chosen size, native process count and result bytes; `commands.csv` records individual command time. Visual runs use their own manifest/checks and do not claim those smoke counters cover the visual subprocesses. `metadata.properties` records OS/JDK/Magick/font identities. External metrics include source digests for reproducibility and optional **sampled process-tree RSS**, not a cgroup peak. Shared pages can be double-counted, brief peaks missed, and unavailable metrics stay null.

Do not commit per-run CSV/JSON/image evidence or freeze measured values into evergreen capacity promises. Archive evidence privately/CI if it must outlive temporary storage.

## Verified local conclusions and production-enablement boundary

Local generated-fixture execution on **macOS x86_64 / ImageMagick 7.1.1-47 / Corretto 21.0.7 / Liberation 2.1.5** established:

- File-fed annotation/caption preserved the tested metacharacters literally. This supports continuing with an owned-file boundary; it does not justify passing untrusted text/paths directly to interpreted operands or weakening file-indirection/security policy.
- Both candidates rendered the sampled pt-BR/text-only/mixed cases. Browser text metrics are not implied, and the production generator still has no text implementation.
- Historical comparison found descending one-native-render-per-size fitting costly: long text caused many process launches. Native built-in fit plus free-height verification reduced that work, but Java2D was substantially cheaper on the long-text/128-box fixtures. This does not override the user's Magick selection or prove acceptable aggregate service cost; keep work/command-count bounds explicit rather than claiming a universal speedup.
- Current shared fitting corrects the retained NFD/long-word size regressions with unchanged input bytes and bounded explicit probes. Pure fitter/launcher tests and native smoke scenes pass; the native 128-area boundary completes locally. The visual profile still fails unresolved alignment/reference gates and rejects an expensive requested-size sweep with `FIT_WORK_LIMIT`; no overall-green or full-glyph claim follows.
- The 40MP **native solid-color baseline failed with pixel-cache exhaustion before text work** under existing limits on this local Q16-HDRI build. The failure is not attributed to text or papered over by larger limits. Admission at 40MP does not guarantee every native operation fits its cache budget; characterize the deployed build and representative media before selecting production limits.

**Selected direction: Magick for authoritative backend text and existing distortion/composition; client-only Konva for initial optional Preview.** Selection follows the user's visual preference, not an all-green feasibility result. Java2D remains comparison evidence, not the active implementation path; no Node/Skia/headless-browser/Java2D migration now. Correctness/resource gate failures or evident preview mismatch may justify revisiting the strategy.

Exact storage schema is still proposed, not implemented. Transfer normal glyph/alignment/line-height cases into implementation regressions without claiming a complete Unicode audit. The shared fitter correction remains harness-only until integrated. Keep historical FAIL/LIMITATION, explicit `FIT_WORK_LIMIT` and the 40MP pre-text capacity rejection visible; they are not passes, and no higher caps, full comparison or server preview are implied.
